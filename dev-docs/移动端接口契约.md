# 移动端接口契约

- 版本：v1.0.0
- 日期：2026-09-11
- 定位：移动端 `iboot-ui/iboot-mobile` 与后端的接口契约，定稿七个扫码动作的路径、入参、出参、幂等键、错误码与扫码内容。
- 上游依据：`dev-docs/业务流程/08-跨模块协作与端到端时序.md` 的"移动端接口契约"与"幂等键全表"；`dev-docs/开发任务安排/01-阶段0-写入路径收口.md` 的幂等键四段规范；七个动作的领域实现（`iboot-module-wms`、`iboot-module-mes`）。
- 任务来源：T5-05（阶段 5）。

**性质说明：本契约是定稿，后端 `controller/app` 包尚未实现。** 本文约定的端点当前均不可调用；实现动作由后续任务承担，实现时必须按本文执行，不再重新设计。与现状的出入（枚举缺 `APP` 取值、部分动作只收数字主键等）集中在"未来实现说明"与各节"实现提示"里交代。

## 一、通用约定

### 1.1 路径前缀

全部移动端业务端点挂 `/app-api` 前缀，与后台 `/admin-api` 区分。资源段与动作段从现有 admin Controller 的 URL 风格推导，与 `@RequestMapping` 一一对应（如 `WmsArrivalOrderServiceImpl.confirmArrival` 在 admin 侧是 `POST /admin-api/wms/arrival/confirm`，移动端即 `POST /app-api/wms/arrival/confirm`）：

| 资源 | admin 侧映射 | 移动端前缀 |
| --- | --- | --- |
| 到货登记 | `/admin-api/wms/arrival` | `/app-api/wms/arrival` |
| 入库单 | `/admin-api/wms/in-order` | `/app-api/wms/in-order` |
| 出库单 | `/admin-api/wms/out-order` | `/app-api/wms/out-order` |
| 领退补料申请 | `/admin-api/mes/material-req` | `/app-api/mes/material-req` |
| 工序任务 | `/admin-api/mes/op-task` | `/app-api/mes/op-task` |
| 报工 | `/admin-api/mes/prod-report` | `/app-api/mes/prod-report` |

### 1.2 认证

复用 admin 用户体系，与 `iboot-mobile` 既有接入决策一致：

- 登录走 `/admin-api/system/auth/*`，双 token 模式（accessToken + refreshToken），不接入租户（请求不带 `tenant-id`）。
- 业务动作请求 `/app-api/*` 时带 `Authorization: Bearer {accessToken}`，鉴权走同一套 token 校验。
- 401 时按移动端既有逻辑用 refreshToken 无感刷新，刷新失败回登录页。
- app-api 端点登录即可调用，不挂 admin 的菜单权限码（`@PreAuthorize` 不用于 app 端点）；动作的合法性由领域层状态机、开工门禁与幂等键保证。

### 1.3 响应包装

统一芋道 `CommonResult` 结构：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | int | 0 表示成功；非 0 为业务错误码 |
| `data` | 随动作 | 见各动作出参表；大多数动作为 `true` |
| `msg` | string | 成功为空串；失败为错误文案（后端已拼好参数，如缺料物料编码） |

### 1.4 幂等键四段格式

沿用阶段 0 确立的四段规范（代码锚点：`WmsCommandBO.of` 与 `WmsSubmitOrderBO` 注释、`MesCommandReqDTO` 注释、`MesOpTaskDomainServiceImpl.buildCommand` 与 `MesMaterialReqDomainServiceImpl.orderKey/lineKey` 的实现）：

```text
{sourceModule}:{sourceBizNo}:{action}:{sourceBizLineNo}
```

| 段 | 取值 | 说明 |
| --- | --- | --- |
| sourceModule | 移动端固定 `APP` | 后台界面是 `UI`，跨模块调用是 `MES` / `APS` / `INTEGRATION` |
| sourceBizNo | 单据编号（单号字符串）或工序任务号 | 优先用扫码所得的业务单号，不用数字主键，命令记录里可读 |
| action | 命令类型枚举名 | 取 `WmsCommandTypeEnum` / `MesCommandTypeEnum` 的枚举名，禁止自造字面量 |
| sourceBizLineNo | 行号 | 整单动作固定 `0`；逐行动作拼行号 |

派生规则：移动端把 `idempotencyKey` 留空时由服务端按上表确定性派生（同一单据同一动作恒为同一个键，连点两次被唯一索引判重）；**报工是唯一例外**——`idempotencyKey` 必填且服务端不派生，见动作六。

### 1.5 错误码

错误码全部引用两模块 `enums/ErrorCodeConstants.java` 中实际存在的常量，按代码原样展示十进制下划线字面量（如 `1_063_011_006`）。移动端收到非 0 `code` 后按 `msg` 原文提示（后端文案已带可执行信息，如缺料清单、未完工前序），不要吞掉重写。

### 1.6 扫码内容

码制（一维码 / 二维码、字段拼接格式）项目当前没有任何文档或代码规定，本文只约定"扫出来的值是什么业务单号"；码制的具体编码方案由标签打印落地时另行补充，不在此发明。需要两个值的场景（如上架的库位码 + 容器码）由页面分两次扫码采集，不做单码多字段拼接。

## 二、动作一：收货确认（confirmArrival）

领域动作：`WmsArrivalOrderServiceImpl.confirmArrival`（`iboot-module-wms`，`service/arrivalorder` 包），走 `WmsCommandService` 命令幂等（`WmsCommandTypeEnum.CONFIRM_ARRIVAL`）。

### 路径与 HTTP 方法

```text
POST /app-api/wms/arrival/confirm
```

### 入参字段表

| 名称 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `arrivalId` | Long | 与 `arrivalNo` 二选一 | 到货登记编号（数字主键） |
| `arrivalNo` | String | 与 `arrivalId` 二选一 | 到货登记单号，扫码所得；领域 BO 原生支持按单号定位 |
| `idempotencyKey` | String | 否 | 留空由服务端按 `APP:{arrivalNo}:CONFIRM_ARRIVAL:0` 派生 |
| `arrivalTime` | LocalDateTime | 否 | 实际到货时间，留空取当前时间；收货员补录场景用 |
| `remark` | String | 否 | 备注，最长 500 |

### 出参字段表

`data` 为 `true`（Boolean），无业务返回值。

### 幂等键格式

```text
APP:{arrivalNo}:CONFIRM_ARRIVAL:0
```

落 `wms_command_record`（唯一索引判重）。重复确认原样返回，不会重复注册批次、重复分流明细。

### 错误码清单

| 错误码 | 常量 | 文案 |
| --- | --- | --- |
| `1_063_011_000` | `ARRIVAL_NOT_EXISTS` | 到货登记不存在 |
| `1_063_011_006` | `ARRIVAL_CANNOT_CONFIRM` | 只有新建状态的到货登记可以确认到货 |
| `1_063_011_009` | `ARRIVAL_LINE_EMPTY` | 到货登记至少包含一条明细 |
| `1_063_001_000` | `WH_NOT_EXISTS` | 仓库不存在 |
| `1_063_001_001` | `WH_DISABLED` | 仓库已停用 |
| `1_062_004_000` | `MATERIAL_NOT_EXISTS`（mdm 段） | 物料不存在 |

### 扫码内容格式

到货单号（`arrivalNo`，WMS 编码规则生成）或供应商送货单号（`wms_arrival.source_no`，来源单号）。扫到送货单号时先按来源单号查到货登记换 `arrivalNo`（未来 app Controller 提供，见第八节），确认动作用 `arrivalNo`。

## 三、动作二：上架过账（confirmInOrder）

领域动作：`WmsInOrderServiceImpl.confirmInOrder`（`iboot-module-wms`，`service/inorder` 包），走命令幂等（`WmsCommandTypeEnum.CONFIRM_IN_ORDER`）+ 行级过账流水键。

### 路径与 HTTP 方法

```text
POST /app-api/wms/in-order/confirm
```

### 入参字段表

| 名称 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `orderId` | Long | 与 `orderNo` 二选一 | 入库单编号 |
| `orderNo` | String | 与 `orderId` 二选一 | 入库单号，扫码所得 |
| `idempotencyKey` | String | 否 | 留空由服务端按 `APP:{orderNo}:CONFIRM_IN_ORDER:0` 派生 |
| `remark` | String | 否 | 备注 |

**实现提示**：目标库位不在本请求里传。库位记在入库单行上（`wms_in_order_line.loc_id`），由生成入库单的动作（到货生成 / 界面建单）指定；`confirmInOrder` 过账时逐行校验库位非空且有效，缺库位抛 `IN_ORDER_LOC_REQUIRED`。移动端扫码的库位码当前用于本地核对"单据行指定库位 == 手上货位"，服务端行级库位覆盖参数是缺口（见遗留）。

### 出参字段表

`data` 为 `true`（Boolean），无业务返回值。

### 幂等键格式

```text
单据级：APP:{orderNo}:CONFIRM_IN_ORDER:0          （落 wms_command_record）
行级过账：APP:{orderNo}:CONFIRM_IN_ORDER:0:POST:{lineNo}   （落 wms_inv_txn，服务端派生）
```

### 错误码清单

| 错误码 | 常量 | 文案 |
| --- | --- | --- |
| `1_063_007_000` | `IN_ORDER_NOT_EXISTS` | 入库单不存在 |
| `1_063_007_002` | `IN_ORDER_CANNOT_CONFIRM` | 只有新建或已确认状态的入库单可以过账 |
| `1_063_007_003` | `IN_ORDER_LINE_EMPTY` | 入库单至少包含一条明细 |
| `1_063_007_005` | `IN_ORDER_LOC_REQUIRED` | 入库明细必须指定目标库位 |
| `1_063_001_000` / `1_063_001_001` | `WH_NOT_EXISTS` / `WH_DISABLED` | 仓库不存在 / 已停用 |
| `1_063_001_004` / `1_063_001_005` | `LOC_NOT_EXISTS` / `LOC_DISABLED` | 库位不存在 / 库位已停用，不能收发存 |
| `1_063_004_005` | `INV_POST_QTY_INVALID` | 库存过账数量必须大于零 |
| `1_063_004_003` | `INV_BALANCE_VERSION_CONFLICT` | 库存余额已被并发更新，请重试 |

### 扫码内容格式

库位码（`wms_loc.code`）+ 容器码（`wms_container.code`，容器本轮【预留】未启用，移动端先只扫库位码）。库位码用于核对上架目标库位；容器码扫到后随备注记录，不参与过账维度（容器维度 `container_id` 当前默认 0）。

## 四、动作三：拣选确认与发货过账（pickOutOrder / confirmOutOrder）

领域动作：`WmsOutOrderServiceImpl.pickOutOrder` 与 `confirmOutOrder`（`iboot-module-wms`，`service/outorder` 包）。任务书说"出库分配与拣选确认"，**代码事实是"出库分配"没有独立领域动作**：PICK 策略选批次与库位目前没有服务实现（`submitOutOrder` 只推进状态，`wms_out_order_line` 的 `from_loc_id` / `batch_id` 由建单或改单时人工指定，见 T0-06 / T0-10 自查遗留），拣选环节只有"拣选确认"与"发货过账"两个动作。

### 4.1 拣选确认

#### 路径与 HTTP 方法

```text
POST /app-api/wms/out-order/pick
```

#### 入参字段表

| 名称 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `orderId` | Long | 与 `orderNo` 二选一 | 出库单编号 |
| `orderNo` | String | 与 `orderId` 二选一 | 出库单号，扫码所得 |
| `idempotencyKey` | String | 否 | 留空由服务端按 `APP:{orderNo}:PICK_OUT_ORDER:0` 派生 |
| `remark` | String | 否 | 备注 |

行为：逐行把 `picked_qty` 置为计划量；单据推进到 `IN_PROGRESS`；销售出库（`SALES_DELIVERY_OUT`）同时触发 OQC 出货检验（事件 → 质检规则解析 → 生成质检任务），非销售出库直接推回 `READY` 等待过账。

#### 出参字段表

`data` 为 `true`（Boolean），无业务返回值。

#### 幂等键格式

```text
APP:{orderNo}:PICK_OUT_ORDER:0
```

#### 错误码清单

| 错误码 | 常量 | 文案 |
| --- | --- | --- |
| `1_063_008_000` | `OUT_ORDER_NOT_EXISTS` | 出库单不存在 |
| `1_063_008_002` | `OUT_ORDER_CANNOT_CONFIRM` | 只有新建或已确认状态的出库单可以过账（拣选沿用此门禁） |
| `1_063_008_003` | `OUT_ORDER_LINE_EMPTY` | 出库单至少包含一条明细 |

### 4.2 发货过账

#### 路径与 HTTP 方法

```text
POST /app-api/wms/out-order/confirm
```

#### 入参字段表

| 名称 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `orderId` | Long | 与 `orderNo` 二选一 | 出库单编号 |
| `orderNo` | String | 与 `orderId` 二选一 | 出库单号 |
| `idempotencyKey` | String | 否 | 留空由服务端按 `APP:{orderNo}:CONFIRM_OUT_ORDER:0` 派生 |
| `remark` | String | 否 | 备注 |

行为：逐行校验来源库位与可用量 → ISSUE 过账（现存扣减）→ 按行上的 `reservation_id` 核销预留 → 单据置 `DONE`。销售出库要求单据处于 `READY`（OQC 放行后），否则抛 `OUT_ORDER_OQC_NOT_PASSED`。

#### 出参字段表

`data` 为 `true`（Boolean），无业务返回值。

#### 幂等键格式

```text
单据级：APP:{orderNo}:CONFIRM_OUT_ORDER:0              （落 wms_command_record）
行级过账：APP:{orderNo}:CONFIRM_OUT_ORDER:0:POST:{lineNo}      （落 wms_inv_txn）
行级核销：APP:{orderNo}:CONFIRM_OUT_ORDER:0:{lineNo}:CONSUME   （落 wms_inv_txn，服务端派生）
```

#### 错误码清单

| 错误码 | 常量 | 文案 |
| --- | --- | --- |
| `1_063_008_000` | `OUT_ORDER_NOT_EXISTS` | 出库单不存在 |
| `1_063_008_002` | `OUT_ORDER_CANNOT_CONFIRM` | 只有新建或已确认状态的出库单可以过账 |
| `1_063_008_010` | `OUT_ORDER_OQC_NOT_PASSED` | 出货检验未通过，不能确认发货 |
| `1_063_008_003` | `OUT_ORDER_LINE_EMPTY` | 出库单至少包含一条明细 |
| `1_063_008_005` | `OUT_ORDER_LOC_REQUIRED` | 出库明细必须指定来源库位 |
| `1_063_001_000` / `1_063_001_001` | `WH_NOT_EXISTS` / `WH_DISABLED` | 仓库不存在 / 已停用 |
| `1_063_001_004` / `1_063_001_005` | `LOC_NOT_EXISTS` / `LOC_DISABLED` | 库位不存在 / 已停用 |
| `1_063_004_001` | `INV_AVAILABLE_QTY_NOT_ENOUGH` | 库存可用量不足 |
| `1_063_004_002` | `INV_ONHAND_QTY_NOT_ENOUGH` | 库存现存数量不足 |
| `1_063_004_003` | `INV_BALANCE_VERSION_CONFLICT` | 库存余额已被并发更新，请重试 |
| `1_063_004_005` | `INV_POST_QTY_INVALID` | 库存过账数量必须大于零 |
| `1_063_005_000` | `RESERVATION_NOT_EXISTS` | 库存预留不存在（行上记了预留却查不到时拦下） |

### 扫码内容格式

库位码（`wms_loc.code`）+ 批次码（`wms_batch.lot_no`）。两个值用于核对单据行上已分配的来源库位与批次（本地校验"行 `from_loc_id` / `batch_id` == 扫到的库位与批次"）；服务端确认动作不收这两个值，行上的分配以建单内容为准。

## 五、动作四：领料确认（confirmMaterialReq）

领域动作：`MesMaterialReqDomainServiceImpl.confirmMaterialReq`（`iboot-module-mes`，`service/materialreq` 包），走 `MesCommandService` 命令幂等（`MesCommandTypeEnum.CONFIRM_MATERIAL_REQ`）。确认是领料三段里唯一改动在库量的一段：领料/补料建 WMS 出库单（`PROD_ISSUE_OUT`）并过账、核销预留、释放未发足的剩余预留；退料建入库单（`PROD_RETURN_IN`）并过账。

### 路径与 HTTP 方法

```text
POST /app-api/mes/material-req/confirm
```

### 入参字段表

| 名称 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | Long | 是 | 领退补料申请编号（数字主键）。**当前领域 BO 只收主键，不支持按申请单号定位**；扫码得到申请单号后先查询换 id |
| `idempotencyKey` | String | 否 | 留空由服务端按 `APP:{申请单号}:CONFIRM_MATERIAL_REQ:0` 派生 |
| `remark` | String | 否 | 确认备注，写进申请备注与 WMS 单据备注 |
| `lines` | List | 否 | 逐行确认参数，**留空表示全部行按剩余量全额确认**（最常见的一次性发料）；只给部分行时未给的行本次不发（按 0 处理），单据落 `PARTIAL` |
| `lines[].lineNo` | Integer | 行内必填 | 申请明细行号 |
| `lines[].confirmQty` | BigDecimal | 否 | 本次确认数量，留空按剩余量（申请量 − 已处理量）全额 |
| `lines[].locId` | Long | 否 | 库位编号：领料/补料是出库来源库位（留空回落预留上记的库位），退料没有预留可依据必须显式给 |

**实现提示**：行级批次调整当前不支持（`MesConfirmMaterialReqBO.Line` 只有 `lineNo` / `confirmQty` / `locId`，批次由预留记的批次出），扫码的批次码用于本地核对，见遗留。

### 出参字段表

`data` 为 `true`（Boolean），无业务返回值。确认后单据终态为 `DONE`（全部发足）或 `PARTIAL`（部分发料，剩余另开补料单）。

### 幂等键格式

```text
命令级：APP:{申请单号}:CONFIRM_MATERIAL_REQ:0      （落 mes_command_record）
```

服务端内部对 WMS 的联动调用各自带键（移动端不必关心，列出备查）：`MES:{申请单号}:CREATE_OUT_ORDER:0` / `MES:{申请单号}:CONFIRM_OUT_ORDER:0` / `MES:{申请单号}:RELEASE_REMAIN:{行号}`；WMS 过账与核销再按行派生 `:POST:{行号}` 与 `:{行号}:CONSUME`。

### 错误码清单

| 错误码 | 常量 | 文案 |
| --- | --- | --- |
| `1_064_013_000` | `MATERIAL_REQ_NOT_EXISTS` | 领退补料申请不存在 |
| `1_064_013_004` | `MATERIAL_REQ_STATUS_INVALID` | 领退补料申请当前状态不允许该操作（只有已提交状态可确认） |
| `1_064_013_012` | `MATERIAL_REQ_NOT_APPROVED` | 超发领料申请未审批通过，不能确认出库 |
| `1_064_013_010` | `MATERIAL_REQ_CONFIRM_QTY_EXCEEDED` | 物料({})本次确认 {}，超过剩余待处理量 {} |
| `1_064_013_011` | `MATERIAL_REQ_CONFIRM_QTY_EMPTY` | 本次确认数量全部为零，没有可发料的明细行 |
| `1_064_013_009` | `MATERIAL_REQ_LOC_REQUIRED` | 物料({})未指定库位，确认发料前请指定库位 |

WMS 联动过账的失败会原样冒泡到移动端（同一事务），常见的是出库侧 `1_063_004_001`（可用量不足）、`1_063_008_005`（来源库位缺失）；退料分支对应入库侧错误码。

### 扫码内容格式

领料申请号（`reqNo`，MES 编码规则生成）+ 批次码（`wms_batch.lot_no`）。申请号定位单据（先换 id）；批次码用于核对发料批次与预留批次一致。**08 文档幂等键全表中领料确认的键写作 `MES:{reqNo}:ISSUE_CONFIRM:{lineNo}`，与实现不符**——实现是整单固定键 `CONFIRM_MATERIAL_REQ:0`（确认是一次性动作，行级幂等由 WMS 内部派生），本文以代码为准。

## 九、未来实现说明

本节交代 `controller/app` 包的实现方式。实现任务必须遵守，不得引入第二套业务逻辑。

### 9.1 包的建法

- 位置：`iboot-module-{模块}/src/main/java/com/iboot/pf/module/{模块}/controller/app/{资源}/`，类名 `App{资源}Controller`（如 `iboot-module-mes/.../controller/app/optask/AppOpTaskController.java`），请求 VO 放同目录 `vo/` 下，命名 `AppXxx{Action}ReqVO`，与 `controller/admin` 平级。
- 路径映射：沿用芋道机制——`controller.app` 包下的 `@RequestMapping("/wms/arrival")` 自动挂 `/app-api` 前缀，`controller.admin` 包挂 `/admin-api`，两个 Controller 的资源段写法一致。
- 端点只做三件事：校验入参、把扫码单号换成主键（需要时）、组装领域 BO 并调用领域 Service。**禁止在 app Controller 里写业务规则**，状态机、门禁、过账、幂等全部在领域层。

### 9.2 认证

- app-api 与 admin-api 共用同一套 token 体系：移动端登录调 `/admin-api/system/auth/*` 拿双 token，业务请求带 `Authorization: Bearer {accessToken}`，由框架统一校验登录态，app Controller 不额外处理认证。
- 不接入租户，请求不带 `tenant-id`。
- 权限策略：app 端点登录即可调用，不挂 `@PreAuthorize` 与菜单权限按钮；动作能否执行由领域层裁决（状态机拒绝非法迁移、门禁拒绝不满足开工条件的任务），移动端按 `code` 与 `msg` 提示。

### 9.3 与 admin-api 共用领域 Service 的原则

- app Controller 与 admin Controller 注入同一个领域 Service（`WmsArrivalOrderService` / `WmsInOrderService` / `WmsOutOrderService` / `MesMaterialReqDomainService` / `MesOpTaskDomainService` / `MesProdReportDomainService`），一个业务事实只有一条写入路径；移动端不新增 Service，不改领域方法签名。
- 领域 BO 不含 `sourceModule` 校验注解差异处理：app Controller 统一固定 `sourceModule = APP`，移动端请求 VO 里不暴露该字段（与 admin 把 `sourceModule` 写死 `UI` 同构）。
- `idempotencyKey` 派生：除报工外，app Controller 对留空的幂等键按四段格式确定性派生，动作段取命令类型枚举名，`sourceBizNo` 优先取业务单号（扫码所得）而非数字主键——比 admin 现状（`UI:{数字id}:{命令}:0`）更可读，语义等价。
- 单号换主键：领料确认、开工、报工、完工的领域 BO 只收数字主键；app Controller 对扫码入参提供 `xxxNo` → id 的转换（`OpTaskMapper.selectByTaskNo`、`MaterialReqMapper.selectByReqNo` 等查询已存在），或由移动端先调 `/app-api` 的查询接口。收货、上架、拣选的领域 BO 原生支持 `orderNo` / `arrivalNo` 二选一，直接透传。

### 9.4 sourceModule = APP 的枚举追加

`WmsSourceModuleEnum`（MES / APS / WMS / INTEGRATION / UI）与 `MesSourceModuleEnum`（MES / APS / INTEGRATION / UI）当前都**没有 `APP` 取值**。实现任务按"枚举只允许追加"的约定给两个枚举各追加 `APP("移动端作业")`，并同步 `MesCommandReqDTO.sourceModule` 的注释。在此之前任何调用方传 `APP` 都无法通过枚举登记（WMS 侧 `source_type` 列为自由字符串不受影响，但命令记录的来源过滤要对上）。

### 9.5 实现顺序建议

1. 追加两个 `SourceModuleEnum` 的 `APP` 取值（一个提交）。
2. WMS 三个动作的 app Controller（收货 / 上架 / 拣选+发货）。
3. MES 四个动作的 app Controller（领料确认 / 开工 / 报工 / 完工）。
4. 每个端点补 Controller 层用例（继承 `BaseDbUnitTest`，覆盖合法迁移、非法迁移、幂等重复提交三类）。
