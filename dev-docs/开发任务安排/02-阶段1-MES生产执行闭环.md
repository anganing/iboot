# 02 阶段 1 MES 生产执行闭环

- 版本：v1.0.0
- 目标：一张工单从 `DRAFT` 走到 `CLOSED` 全程只用动作端点，`mes_wip_txn` 有完整轨迹，库存三段（预留、出库过账、完工入库）账实一致且可用量无虚占。
- 依据：`dev-docs/业务流程/04-MES生产执行流程.md` 全文，`08-跨模块协作与端到端时序.md` 的"链路二"
- 任务数：31
- 前置：阶段 0 全部 18 个任务审查通过

## 阶段背景

MES 的表结构、枚举、CRUD 已全部就绪，缺的是动作层：135 个 Controller 端点全是 CRUD，`MesApiServiceImpl` 是空类，7 个门面抛 `UnsupportedOperationException`，`mes_wip_txn` 生产代码从未写入。

本阶段建的是"动作 → 状态机 → 推进链 → 库存联动"这条骨架。骨架建好后，阶段 2 的质量门禁才有地方挂。

## 并行组

| B | T1-07 T1-08 T1-09 T1-10 T1-11 T1-12 T1-13 T1-14 T1-15 T1-16 T1-17 | 领域动作，依赖 A，组内有少量串行（见各任务） |

| F | T1-32 | 补充任务，执行过程中发现的主数据缺口，依赖 E（要动 mdm 前端） |

## 统一约定

本阶段所有领域动作遵守：

| 约定 | 说明 |
| --- | --- |
| 幂等 | 走 `MesCommandService`（T0-02 已建），键格式见 `08` 的幂等键全表 |
| 状态校验 | 调对应状态机的 `next(current, action)`，非法迁移由状态机抛错 |
| 在制流水 | 每次状态变更调 `MesWipTxnRecorder`（T1-06 建），不在各动作里手写 DO |
| 事务 | 动作方法加 `@Transactional(rollbackFor = Exception.class)`，跨模块调用在同一事务内 |
| 跨模块 | 只走 `api` 门面，禁止跨库 JOIN，批量取数 |
| 乐观锁 | 推进 `mes_op_task` / `mes_prod_order` / `mes_work_order` 时带 `version` 条件 |

**偏差说明**

1. **`KitOrIssuedChecker` 的判定口径：只拦 `must_issue_before_start = true` 的物料，要求它们的净发料量达到本工序需求量。** 三份文档给了三个说法，按 04 文档定夺，理由如下。
   - **为什么是"已发料"而不是"齐套"**：门禁在车间现场触发，工序要开工料必须在工位上。仓库账上有但没发下来，工人手里没料照样干不了活。`must_issue_before_start` 这个字段名本身就把答案写死了——"必须在开工前发料"。
   - **04 文档"齐套或已发料"的"或"指什么**：指这一关的两条放行路径。必发料走"已发料"，非必发料（边做边领、倒冲）走"齐套"，而后者由齐套检查动作负责、不阻塞开工。这也解释了 04 文档"数据来源"列为什么同时列了 `mes_kit_snapshot` 与 `mes_material_req_line`。任务书条目只描述了会拦人的那一支，两者不矛盾。
   - **与 T1-09 齐套判准的关系**：齐套判的是 `可用量 + 已预留 + 已领用 >= 需求量`（料能不能凑齐，**计划口径**），门禁判的是 `已发料 >= 需求量`（料到没到工位，**现场口径**）。前者通过不代表后者通过，**这正是领料三段存在的理由**——齐套只说明料凑得齐，中间还要走申请、提交、确认三步料才到车间。两者共用同一个 `MesKitRequirementExpander` 算需求量，不会出现"齐套判齐了而门禁按另一个需求量算缺料"。
   - **按 `processed_qty` 累计而不是只认 `status = DONE` 的行**：T1-11 引入了部分发料，部分发的行状态是 `PARTIAL` 而它已发下去的量是实打实的。只认 `DONE` 会把已发的 80 算成 0、缺口虚高到 100，把只差一点的工彻底挡住。这个口径与 T1-09 的 `issued_qty = Σ processed_qty` 一致，已由"发 80/100 判缺 20"一例锁死。
2. **补了任务书没提的退料扣减。** 领料/补料的 `processed_qty` 加、退料的减，判的是"车间此刻净持有多少"。领 100 又退 30，车间手上只剩 70，需要 100 就是缺 30。不扣的话退料后门禁仍认为料齐，工人到现场发现料被退回去了。**与 T1-09 的 `issued_qty` 快照列有一个差异：那一列未扣退料，有退料时两处会差一个退料量。** 见遗留 5。
3. **三档申请范围（工序级 / 作业工单级 / 生产工单级）。** 任务书只说"查 `mes_material_req_line`"没说范围。只看工序级申请的话，按整单一次领料的场景会被误判成缺料——料明明在车间，门禁却不认。三档一次 OR 查询完成，不逐档查。
4. **`MesStartGateItem.enabled` 签名多了 `MesStartGateContext` 参数**（任务书是 `enabled(OpTaskDO task)`）。`FirstArticleChecker.enabled` 要读 `route_op.fai_flag`，光有 `OpTaskDO` 拿不到——`mes_op_task` 上没有这个字段。
5. **新增两个清单外文件。** `MesStartGateContext`（任务书在 `check` 签名里用到了它但没列进清单）与 `MesStartGateNames`（五个校验项名称集中定义；名称会进预检结果返回给前端也会进日志，散在各实现类里写字面量，改一个名字就和历史记录、前端映射对不上）。两者都在本任务独占目录内。
6. **`MesStartGateChecker` 加了 `inspect` 入口。** 任务书只要求"任一失败抛错"的 `check`，但那样 `MesStartGateResult` 就没有存在意义（`check` 是 void + 抛异常）。两个入口对应两种问法：`check` 回答"能不能开工"（供 T1-13 的 `start`），`inspect` 回答"现在为什么不能开工"（供作业页预检，一次列全所有不满足项，车间才能一趟把料领齐、把工装准备好，而不是修一项再点一次开工试试）。`inspect` 只吞 `ServiceException`——门面调用失败、空指针这类系统故障继续往外抛，把它们当成"这一项没通过"会让车间对着"资源不可用"排查半天，实际是 mdm 挂了。
7. **`impl/` 下五个类不带 `Mes` 前缀，顶层四个带。** 这个不一致来自任务书本身（它写的就是 `MesStartGateChecker` 与 `PrevDoneChecker` 混用）。按任务书命名以便审查方对文件名，且 `gate/impl/` 包已与 codegen Service 区分得很清楚。
8. **资源门面叫 `ResourceApi` 不是任务书写的 `ResApi`**，方法是 `getResourceMap(Collection<Long>)` 与 `getResourceCalendarList(Collection<Long>, LocalDate, LocalDate)`（闭区间，查当天传起止同一天）。
9. **`ResourceAvailableChecker` 多判了一条"资源已停用"。** 任务书只列了排班与并行产能两条。`ResourceApi.getResourceMap` 不过滤停用资源（它是通用批量取数，过滤了别的调用方就查不到停用资源的名称），而停用的设备排了工也开不了，所以 MES 侧必须自己判 `status`。并行产能没配或配成 0 时按 1 处理——按无上限处理会让一台设备被排上十道工序。只数 `RUNNING` 不数 `PAUSED`：暂停的工序占着工件但设备是空的，算占用会挡住"暂停一道去插一道急件"这种常规操作。本工序自己排除掉，重复开工由状态机拦，不该在这里表现成产能不足。
10. **`FirstArticleChecker` 把"已有过报工"放在 `enabled` 而不是 `check` 里。** 这样预检结果如实显示"这一项本次跳过"，而不是显示"通过"——车间看到"首件通过"会以为首件已经检过了。判定要求 `status = DONE` **且**结论合格两个条件同时成立：`MesQcTaskStatusEnum` 类注释明确"结论与合格、不合格数量在 DONE 时才落定"，只看结论会读到检验中途的中间值。让步接收（`CONCESSION`）不算通过——它要走不合格品处置单，门禁不替处置流程放行，用 `MesQcConclusionEnum.isQualified` 保证，有独立用例。
11. **`PrevDoneChecker` 只认 `DONE` 与 `SKIPPED`，不认 `CANCELLED`**（按任务书）。取消是异常终止，一道工序被取消通常意味着整条链要重排，当成"已完成"会让后序在已废弃的链上开工。并行组范围限定在同一作业工单内：`parallel_group` 只是个字符串标记，不限工单的话别的工单里同名的组会被算进来。
    - **【调度方整改批注｜本条后半段是缺陷，已由调度方修正】** T1-13 的执行 AI 报出并经调度方核实：下达时并行组是按**整张生产工单**分组的（`MesOrderExpandHelper.expand` 里 `chainTasks(tasks)` 的 `tasks` 是 `createOpTasks` 返回的整单全部工序任务），而作业工单是按**工作中心**建的（`createWorkOrders` 返回 `Map<工作中心, 作业工单>`）。所以同一个并行组的工序会因工作中心不同落进不同的作业工单——04 文档的"喷漆 ‖ 标识"正是这种情形，项目自己的 fixture 也是这么造的（`MesProdOrderDomainServiceImplTest.parallelRoute()`：`routeOp(PAINT, seq=30, WC_PAINT, GROUP_A)` 与 `routeOp(MARK, seq=30, WC_MARK, GROUP_A)`）。按 `workOrderId + parallelGroup` 取组会把这个最典型的并行组切成两个单元素组，"并行组全部完工"当场退化成"代表工序完工"，**装配会在标识还没做完时就被放行**。正确范围是"同一生产工单内同名 `parallel_group` 才是一个组"。调度方已改 `PrevDoneChecker.requiredTasks` 的查询维度为 `prodOrderId + parallelGroup` 并补跨作业工单并行组用例。T1-13 侧本就按生产工单取，两处口径现已一致。

12. **技能有效性判定放在 MES 侧。** `SkillApi.getMemberSkillList(Collection<Long>)` 是裸批量取数，不过滤 `status` 也不过滤有效期（mdm 的 `SkillService` 里有带日期判定的 `getMemberSkillListByUserId(Long, LocalDate)`，但门面没暴露它，且是单人版）。DTO 上 `status` / `effectiveDate` / `expiryDate` 三个字段齐全，MES 侧完全做得到，故不改 mdm。停用、未生效、已过期三种无效情形各有独立用例。同一技能多条记录取最高等级——按查询顺序取会随机拿到升级前的旧等级，把有资质的人挡在外面。
13. **有技能要求但取不到操作者时直接拦。** 无法证明干活的人有资质就等于不满足；放过去等于把资质校验变成"填了就查、不填就免检"，那还不如不做这一关。派给班组（`operator_id = 0`）时取不到人也是同样处理——班组里谁来干还没定。取消状态的派工不算派了人。
14. **工装用 `getToolList()` 过滤而不是给 `ToolApi` 加 `getToolMap(ids)`。** `ToolApi` 只有 `getToolList()` 与 `getRouteOpToolList(routeOpIds)`，缺按 id 批量取。加方法要改 mdm 现有文件，与"纯追加、不改 mdm 现有文件"冲突；`getToolList()` 是一次查询不产生 N+1，工装主数据规模在制造业是百级到千级，门禁又是低频动作，代价可接受。已列入遗留。
15. **消息里的工序名取 `OpTaskDO.opName` 快照而不是回查 mdm。** `RouteOpRespDTO` 没有 `opName`（`mdm_route_op` 表本身也只有 `op_id`），而 MES 侧下达时已把 `opName` / `opCode` / `seq` / `parallelGroup` / `keyFlag` 都落成快照，门禁没必要为一个名字再跨模块调一次。
16. **主数据查不到时退化成"不拦"。** 路线工序、资源查不到时不抛错。门禁的职责是拦住确定不满足的情况，不是拦住查不到数据的情况——否则一条脏数据能让整个车间停工。有专门用例锁死。
17. **不碰的东西按约束严格执行**：作业工单 `PENDING → READY` 的推进不做（调度方裁到 T1-13）；不读 `mes_op_task.kit_status`（T1-09 确认该列不存在），完全按领料行判定；不实现 `start` 动作本身；不新增门禁配置表，开关一律取自已有主数据标志（`fai_flag`、`res_id` 是否分配、`route_op_id` 是否挂上）。

**偏差说明**

1. **作业工单的 `scrap_qty` 无处落地**：`mes_work_order` 表**没有这一列**（dbx 查 `information_schema` 确认，H2 与 `WorkOrderDO` 也没有）。所以任务书口径表里"作业工单 `scrap_qty`"这一格在当前库结构下是空的，只推 `completed_qty`，报废在生产工单一级按各工序之和汇总。要在作业工单看到分段报废量得先加列，不在本任务范围。
2. **上卷用"重算"而不是"增量累加"。** 两级工单的 `completed_qty` 每次都从工序任务重新算（取末道工序值 / Σ报废），这让**取消报工不需要另写一套反向公式**：把工序级数量扣回去再重算一遍，两级自然回到正确值。任务书说"反向扣减三级数量"，实际只有工序级需要真的做减法。
3. **报工不把工序任务推到 `DONE`**，尽管 04 的流程图画了这条线。理由：工序 `RUNNING → DONE` 是 `finishOpTask` 的职责（T1-13，且要求"合格 + 报废 = 计划数"严格相等）。如果报工也推，`finishOpTask` 当场变成死代码（最后一次报工落地时工序已是 `DONE`，人再点完工必然抛"状态不允许"），同一个业务事实就有了两条写入路径。任务书对这一级的措辞也是"工序**可**完工"而不是"置 `DONE`"，故按判定实现（公开 `qtyReached`），推进留给完工动作。
4. **`finishOpTask` 必须触发上卷，任务书没写这一步。** "本段全部工序 `DONE` / `SKIPPED` → 作业工单 `DONE`"只可能在完工的那一刻成立，而最后一次报工发生在完工**之前**——上卷只挂在报工上的话，作业工单永远等不到 `DONE`，点名的那条验收永远达不到。所以 `doFinish` 末尾以零增量调 `propagate`（只重算不改数量）。
5. **新增 `PROD_REPORT_QTY_EXCEEDED`（任务书没要求）拦超报。** 根因是 `MesBusinessRules.validateFinishQty` 要求**严格相等**且属禁止改动清单：累计一旦超过计划数，那道工序永远凑不出这个等式，会被**永久卡在 `RUNNING`**，既完不了工也推不动后序。判定用 `>=` 只是为了容纳"刚好等于"，不代表允许超报。
6. **新增 `PROD_REPORT_CANCEL_OP_TASK_DONE`**：已完工工序的报工不许取消。完工时按"合格 + 报废 = 计划数"校验并置了 `DONE`，抽掉一笔报工会让工序停在"数量不够却已完工"，而 `DONE` 是终态、没有回退边，自己圆不回来。要改数量必须先撤完工，而撤完工本轮没有这个动作。
7. **报工要求工序处于 `RUNNING`**（任务书没写状态前置）：待开工的还没开始干，`PAUSED` / `QC_WAITING` 当下不在加工，`DONE` 的账已封版。
8. **`submitReport` 的幂等键必填、服务端不派生。** 键格式 `UI:{taskNo}:REPORT:{seq}` 里的 `seq` 是"第几次报工"，服务端按已有报工数派生的话，每次重试都会算出一个新 `seq`、每次都建新记录，幂等当场失效——而报工是最容易被重复提交的动作（扫码枪连扫、弱网重发）。其余动作的键仍可留空派生。
9. **报工流水挂在报工单上，不用 Recorder 的 `recordReport` 便捷方法。** 那个方法把来源业务记成工序任务，一道工序分批报三次就有三条同 `biz_no` 的流水，事后分不清是哪一次；改记 `PROD_REPORT` + 报工单号可从流水直接反查报工记录。`from` / `to` 相应记报工单自己的状态，与 `bizType` 指向的主体保持一致。
10. **取消用 `REPORT` 类型 + 负数量表达冲销**：九种事务类型里没有"取消报工"，取语义最近的一个，与 WMS 侧红字冲销同形。
11. **两个清单外的东西**：`MesCancelReportBO`（取消需要 `reportId` + 原因 + 命令幂等字段，塞进提交 BO 会得到一个一半字段永远为空的载体）；`MesCommandTypeEnum` 追加 `CANCEL_PROD_REPORT`（取消是状态推进型、报工记录那一列已被提交占用，只能走命令记录）。
12. **末道工序并列时取最小值**：末尾是并行组（多道同 `seq`）时，段产出取组内 `completed_qty` 的最小值——只有全部并行工序都做完的那部分件数才算真流过了这一段。任务书只说"末道工序"，没定并列规则。
13. **负数报工拦截**（复用 `QTY_MUST_BE_POSITIVE`）：负数会把累计值静默扣小，比报错难查得多。
14. **报工不校验 `workerId` 是否真实存在**（codegen 的建单路径会校验）。报工是现场高频动作，为一个可读字段多跨一次模块调用不值得，干活人的资质在开工门禁那一关已按技能校验过。
