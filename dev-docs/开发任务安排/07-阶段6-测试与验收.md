**三、关键修复：Flowable 在 H2 上建 ACT_* 表失败**

原报错链：`Failed to load ApplicationContext` → `bpmProcessInstanceApiImpl` 注入失败 → `runtimeServiceBean` → `processEngine` FactoryBean 创建失败 → `FlowableException: couldn't create db schema: create table ACT_HI_TSK_LOG` → `JdbcSQLNonTransientException: Unknown data type: "IDENTITY"`。

根因（已实测验证）：**Flowable 8.0.0 自带的 H2 建表脚本自身有 bug**——`flowable.h2.create.common.sql` 第 525 行 `ID_ identity`、`flowable.h2.create.engine.sql` 第 98 行 `LOG_NR_ identity`，把 `identity` 当数据类型用（H2 1.x 写法）。H2 2.3.232 已废弃该类型，解析器直接报 SQLSTATE 50004，建表中断。对照 MySQL 脚本同一张表写的是合法的 `ID_ bigint auto_increment`。

注意 `MODE=MYSQL` 只改变 H2 的 **SQL 语法解析**，不改变 JDBC 元数据自报的产品名（仍是 H2），所以 Flowable 的自动探测（`DbUtil.determineDatabaseType` 读 JDBC metadata）依然选中那份有 bug 的 H2 脚本——**光调 URL 参数解决不了**。

修法：新增测试专用 `FlowableH2DialectConfig`，注册 `ProcessEngineConfigurationConfigurer` Bean 显式 `setDatabaseType(DATABASE_TYPE_MYSQL)`，强制 Flowable 走 MySQL 方言 DDL。成立依据有二：其一，MySQL 版脚本在 `MODE=MYSQL` 的 H2 上实测可完整执行（common 100/100、engine 56/56、history 23/23 全部成功，`ENGINE=InnoDB ... COLLATE utf8_bin` 表后缀、`datetime`、`TINYINT`、`longtext` 等方言 H2 均接受）；其二，探测逻辑只在 `databaseType` 为 null 时才跑（`AbstractEngineConfiguration`：`if (databaseType == null) { initDatabaseType(); }`），显式设定后不会被覆盖回去。

**排除了的方向**：① 改 `script/h2-schema-convert.py` 或 `schema.sql`——那是改错文件，`ACT_*` 由引擎自建，手工 DDL 违反 CLAUDE.md 红线；② 配 `flowable.database-type`——Flowable 的 Spring Boot starter **根本没暴露这个属性**（`FlowableProperties` 只有 `databaseSchemaUpdate`/`databaseCatalog`/`databaseSchema`），配了不生效；③ 换/降 H2 版本——波及全仓各模块 `BaseDbUnitTest`，且 H2 1.x 早已停止维护，为绕一个三方 bug 引入更大技术债，已避免。

1. **fixture 的 `PilotLine` 不携带 WMS 编号**：`WmsFixture.createWarehouseWithStock()` 返回一个独立的 `WmsStock` record，`PilotLine` 上的 `whId`/`zoneId`/`locId` 始终是 0 占位。齐套要按仓库过滤可用量、补料要指定仓库与库位，因此必须接住返回的 `WmsStock` 用它的真实编号——直接用 `line.whId()` 会撞 `WH_NOT_EXISTS`（`WmsWarehouseServiceImpl.validateWh`）。这是 T6-01 自查没提到、但后续用例都会遇到的一点。
2. **试点 BOM 的虚拟件没有子件 BOM**：`MdmFixture` 只把虚拟件本体挂进 BOM，虚拟件自己的生效 BOM 得由用例补。不补的话整单齐套会抛 `KIT_CHECK_PHANTOM_BOM_MISSING`（04 文档要求的显式报错，不是静默跳过）。本类在 `@BeforeEach` 里建了一份虚拟件 BOM（子件用量 3）来驱动向下展开。
3. **"改 BOM 不影响工单"的构造**：MDM 不允许改已启用 BOM 的明细，只能新起一版；且生效日期必须 **≤ 今天**，写明天会被 `getEffectiveBom` 的 `effectiveDate.isAfter(date)` 过滤掉，看起来像"改动没生效"。首轮就踩了这个坑（曾误用 `now().plusDays(1)`）。
4. **替代料场景不需要另起产线**：新造成品物料就得连工艺路线一起建（下达要解析生效路线），代价大。改为复用试点产线——主料取"虚拟件子件"（新建、从没入过库，需求 300 全缺），替代料取试点 PICK 件（真实过账 500 在库），"主料不足、替代料充足"就是真实账面事实。
5. **整单齐套的汇总结论取决于全部行**：虚拟件子件零库存时整单是 `PARTIAL_KIT`（常规料齐 + 子件缺），不是 `FULL_KIT`。首轮把某一行的结论当成了整体结论（已修正为按行断言 + 单独断言汇总结论）。
6. **补库存复用 `InOrderApi` 真实过账**：显式带 `uom_code`/`loc_id` 等调用方快照列（T6-01 自查的提示），幂等键带上物料编号以免同用例内多物料撞键。
