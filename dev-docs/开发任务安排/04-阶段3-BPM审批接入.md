## B 组：五个接入点

B 组各任务都做三件事：发起改造、监听器、回调回写。**互不重叠。**

### 共性整改说明（T3-03~07 共用，五处同一种写法）

**问题**：五个 APPROVE 回调里的领域动作（`executeDisposition`、`confirmCountDiff` 逐行过账、`confirmMaterialReq`、
跳序生效推后序、报废出库过账）原先都以 `REQUIRED` 传播跑在 Flowable 事务内。动作一旦失败就把事务标成
rollback-only，`onEvent` 虽然 catch 住不外抛，Flowable 在最外层提交时仍抛 `UnexpectedRollbackException`
——**审批终态被整体回滚**，表现为"审批人点了通过，单据还在审批中"。这与 07 文档
「领域动作失败时单据置一个审批通过但执行失败的状态，由人工重试执行，不要让流程回滚」直接冲突。

**改法**：新增 `MesBpmApprovalActionExecutor`（mes）与 `WmsBpmApprovalActionExecutor`（wms，同构两份，
两模块不互相依赖），提供 `executeAfterCommit(actionName, action)`：有事务时注册
`TransactionSynchronization.afterCommit`，无事务时立即执行；两种情况下动作都跑在
`PROPAGATION_REQUIRES_NEW` 的独立事务里，异常在执行器内部吞掉并记 error 日志。五个接入点一律经它执行领域动作。

**为什么选 afterCommit 而不是就地 `REQUIRES_NEW`**（这是选型的核心，不是风格偏好）：回写方法里的第三层
条件 UPDATE（`WHERE approval_status = RUNNING`）**已经持有该业务单据的行锁**。若在同一个方法内改用
`REQUIRES_NEW` 起子事务去执行领域动作，子事务要改/要读的还是同一行，等的是父事务尚未提交的那个锁——
**自己等自己**，只会锁等待超时，把"动作会失败"升级成"动作必然卡死"。REQUIRES_NEW 能独立提交的前提是
父事务已经释放锁，那等价于必须挂到 afterCommit。所以 afterCommit 不是两种可选方案里挑了一个，
而是这个约束下唯一能同时满足"不回滚流程"和"不自锁"的写法。次生要求：Spring 触发 afterCommit 时
当前事务资源尚未从 `TransactionSynchronizationManager` 清理（清理在 `cleanupAfterCompletion`），
此时 `REQUIRED` 会"加入"那个已提交完的事务、写入永不落库，故执行器里固定 `REQUIRES_NEW`。

**可观测与人工重试口径**（不新增表、不扩列，各接入点用自身既有状态表达）：

| 接入点 | 失败后停留的可查状态 | 人工重试入口 |
| --- | --- | --- |
| T3-03 让步接收 | `mes_disposition.status = APPROVED` 且 `target_biz_no` 为空 | 既有 `/mes/disposition/execute` |
| T3-04 报废处置 | 同上 | 同上 |
| T3-05 盘点差异 | `wms_count_order.approval_status = APPROVE` 而 `status` 仍 `COUNTING`、行仍 `DIFF` | 既有 `/confirm-diff`（门禁此时已放开） |
| T3-06 超发领料 | 通过侧无自动动作（确认本就是人工第四段），回写只放开门禁；驳回侧若收尾失败：`approval_status = REJECT` 而单据仍 `SUBMITTED`、预留仍占着 | 既有取消端点：`approval_status` 已是终态，`doCancel` 的 `RUNNING` 门禁不再命中，取消即释放预留 |
| T3-07 工序跳序 | `mes_op_skip_record.status = EFFECTIVE` 而 `mes_op_task.status` 仍 `READY` | `MesOpSkipDomainService.takeEffectApprovedSkip(recordId)`，幂等可重跑 |

重试路径的幂等由既有约束兜住：命令记录唯一索引、`mes_wip_txn.idempotency_key` 唯一索引、
库存过账的 `idempotency_key` 判重、工序任务 `version` 乐观锁，因此补跑不产生第二笔过账或第二条流水。

**同批修的第二个坑：回写方法里"单据不存在"必须静默返回，不许抛异常。**
"不抛异常"这条红线（07 自查清单第 8 条）落点是 `onEvent` 整条调用链，不是只有监听器那一层——
回写方法在 Flowable 事务内抛出的异常即使被监听器的 try-catch 吞掉，事务早已被
`@Transactional(rollbackFor = Exception.class)` 标记 rollback-only，流程提交时照样
`UnexpectedRollbackException`。本轮五个回写方法统一按 id 取单，取不到记 warn 后 return
（流程还在跑而单据被逻辑删是可能发生的）；`cancelAfterApprovalRejected` 与
`takeEffectApprovedSkip` 相反，它们跑在事务提交后的独立事务里，查不到就该抛，让重试看得见原因。
五个任务各补一例 `*_missing*IgnoredSilently` 把这条契约钉成断言，不靠"监听器有 catch"蒙过去。
