### T5-01 批次正向追溯查询

- 依赖：阶段 2 完成
- 依据：`08-跨模块协作与端到端时序.md` 的"正向追溯"流程图与五张事实表
- 独占文件：
  - 新增模块位置：`iboot-module-mes/src/main/java/com/iboot/pf/module/mes/service/trace/`（`MesTraceService` 与 `Impl`、`MesTraceForwardResolver`）
  - 新增 `.../mes/service/trace/bo/`（`MesTraceQueryBO` `MesTraceNodeBO`）
  - 新增 `.../mes/controller/admin/trace/TraceController.java` 与其 `vo/`
  - 新增对应测试类
  - `system_menu` 新增菜单与权限（dbx）
- 做什么：
  1. `traceForward(MesTraceQueryBO)`：起点是原料批次（`lotNo` 或 `batchId`），输出到出货客户的完整链路。
  2. 查询路径（**每一步都走门面批量方法，禁止跨库 JOIN**）：
     - `InventoryApi` 查该批次的 `ISSUE` 方向流水（`biz_type` 为 `PROD_ISSUE_OUT`）
     - `OutOrderApi` 按流水的 `biz_no` 取出库单，拿 `prod_order_no`
     - MES 内部查生产工单（含 `bom_version` `route_version`）
     - MES 内部查该工单的工序任务与在制流水
     - `InOrderApi` 查该工单的完工入库单（`biz_type` 为 `PROD_FINISH_IN`），拿成品批次
     - `InventoryApi` 查成品批次的 `SALES_DELIVERY_OUT` 流水
     - `OutOrderApi` 取出库单的 `customer_id`，`CustomerApi` 补客户名称
  3. 返回结构是树：`MesTraceNodeBO` 含 `nodeType`（批次 / 出库单 / 生产工单 / 工序任务 / 入库单 / 客户）、`bizNo`、关键字段快照、`children`。
  4. **一次查询拉出完整链路**：不许让前端逐层调接口。深度上限 10 层（防循环，超限截断并标注）。
  5. 起点支持三种：批次号、工单号、销售出库单号（工单号与出库单号从链路中间切入）。
  6. Controller 加 `GET /trace/forward`，权限码 `mes:trace:query`；新增菜单"批次追溯"。
  7. 测试：造一条完整链路数据（原料入库到领料到报工到完工入库到发货），断言树的层级与节点数正确；断言无 N+1（用调用计数或日志验证）。
- 不做什么：
  - **不做反向追溯**（T5-02）
  - 不做前端（T5-03）
  - 不做看板与 KPI
  - 不做导出（T5-03 前端负责）
- 验收：
  - 一次调用返回完整树
  - 测试断言层级与节点数正确
  - `mvn -pl iboot-module-mes -am test` 全绿

### T5-02 批次反向追溯查询

- 依赖：阶段 2 完成
- 依据：`08-跨模块协作与端到端时序.md` 的"反向追溯"流程图
- 独占文件：
  - 新增 `.../mes/service/trace/MesTraceBackwardResolver.java`
  - `.../mes/service/trace/MesTraceServiceImpl.java`（仅新增 `traceBackward` 方法，**不改 T5-01 写的 `traceForward`**）
  - `.../mes/controller/admin/trace/TraceController.java`（仅新增一个端点）
  - 对应测试类新增用例
- 做什么：
  1. `traceBackward(MesTraceQueryBO)`：起点是成品批次，输出到原料供应商的完整链路。
  2. 查询路径：
     - `InOrderApi` 查该批次的完工入库单（`biz_type` 为 `PROD_FINISH_IN`），拿 `prod_order_no`
     - MES 内部查生产工单（含两个版本号）
     - MES 内部查该工单的领料明细 `mes_material_req_line`，拿 `batch_id` 与 `lot_no`
     - `BatchApi` 批量取原料批次，拿 `supplier_id` `supplier_lot_no` `furnace_lot_no`
     - `SupplierApi` 补供应商名称
     - 挂上该工单的质检任务（各检验点结论与检验方案版本）与在制流水
  3. 返回结构复用 `MesTraceNodeBO`。
  4. Controller 加 `GET /trace/backward`，权限码复用 `mes:trace:query`。
  5. 测试：同一条链路数据，从成品批次反查，断言能找到全部原料批次与供应商；断言质检结论已挂上。
- 不做什么：
  - 不改 T5-01 写的正向逻辑
  - 不做前端
- 验收：
  - 反查能找到全部原料批次与供应商
  - `mvn -pl iboot-module-mes -am test` 全绿

- 依赖：T5-01 T5-02
- 依据：`08-跨模块协作与端到端时序.md` 的"追溯查询的实现要求"；`dev-docs/后台UI开发规范.md`
- 独占文件：
  - 新增 `apps/web-ele/src/api/mes/trace/index.ts`
  - 新增 `apps/web-ele/src/views/mes/trace/index.vue` 与 `data.ts`
  - 后端导出端点：`.../mes/controller/admin/trace/TraceController.java`（新增 `GET /export-excel`）
- 做什么：
  1. 查询区：起点类型（批次号 / 工单号 / 销售出库单号）+ 起点值 + 方向（正向 / 反向）。
  2. 结果区用树形表格展示链路（`useVbenVxeGrid` 的树形模式，或 `ElTree` 配合明细面板——**优先 vxe 树形表格**，符合 UI 规范的"列表一律 `useVbenVxeGrid`"）。
  3. 每个节点显示：节点类型（字典映射中文）、业务单号、物料编码名称、批次号、数量、时间、关键快照（工单节点显示 BOM 与工艺版本，批次节点显示供应商与供应商批次，质检节点显示结论）。
  4. 导出 Excel：后端加导出端点，把树拍平成行（带层级列），供客户审核使用。
  5. 新增菜单"批次追溯"，权限码 `mes:trace:query` 与 `mes:trace:export`，dbx 加菜单与权限按钮。
- 不做什么：
  - 不做看板、图表、KPI
  - 不改追溯查询的后端逻辑（除新增导出端点）
- 验收：
  - `pnpm typecheck` 与 `pnpm build` 通过
  - 1440 与 1920 宽度下树形表格不撑宽
  - 导出的 Excel 含层级列且节点信息完整

### T5-04 部署交付脚本 sql/deploy

- 依赖：阶段 3 与阶段 4 全部审查通过
- 依据：`08-跨模块协作与端到端时序.md` 的"库结构与初始数据"
- 独占文件：
  - 新增目录 `sql/deploy/` 及其下全部文件
  - 新增 `script/export-deploy-sql.sh`（或 `.ps1`，按项目习惯选一种）
- 做什么：
  1. 建 `sql/deploy/` 目录，**与芋道原生脚本隔离**（不动 `sql/` 下已有文件）。
  2. 写导出脚本 `script/export-deploy-sql.sh`，**可重复执行，禁止手工拼 SQL**。脚本从开发库（`ruoyi-vue-pro-20260817`）导出：

     | 文件 | 内容 | 导出范围 |
     | --- | --- | --- |
     | `01-schema.sql` | 全量表结构 | 所有表的 DDL，不含数据 |
     | `02-menu.sql` | 菜单与按钮权限 | `system_menu` 全量 |
     | `03-role.sql` | 角色与授权 | `system_role`、`system_role_menu` |
     | `04-dict.sql` | 字典 | `system_dict_type`、`system_dict_data` |
     | `05-code-rule.sql` | 编码规则 | `infra_code_rule` 全量（MDM 18 条 + WMS + MES + APS） |
     | `06-wms-strategy.sql` | 仓储策略样例 | `wms_strategy` |
     | `07-qc-rule.sql` | 质检规则与检验方案样例 | `mes_qc_rule`、`mes_qc_plan`、`mes_qc_item` |
     | `08-aps-strategy.sql` | 排程策略样例 | `aps_strategy` |
     | `09-bpm-process.sql` | 五个审批流程定义 | `bpm_*` 相关配置表（**不含 `ACT_*`，引擎自建**） |

  3. 写 `sql/deploy/README.md`：版本号、执行顺序、每个文件的作用、变更记录表（日期、版本、改了什么、谁改的）。
  4. 用一个空库实测：按 README 的顺序执行全部脚本，启动应用，确认：
     - 菜单树完整，三个隐藏菜单确实隐藏
     - 编码规则齐全（创建主数据不抛"编码规则不存在"）
     - 字典完整（列表页枚举列显示中文不显示原始值）
     - 五个审批流程可发起
  5. 实测结果写进 `README.md` 的"验证记录"一节。
- 不做什么：
  - **不动 `sql/` 下已有的芋道原生脚本**
  - **不导出业务数据**（工单、库存、流水这些测试数据不进交付脚本）
  - 不手工编辑导出的 SQL（要改就改导出脚本）
  - 不导出 `ACT_*` 表结构
- 验收：
  - 空库执行后应用可启动且可进入试点配置
  - 导出脚本可重复执行（连跑两次结果一致）
  - README 的验证记录完整

### T5-05 移动端接口契约定稿

- 依赖：阶段 2 完成（七个动作的领域实现已就绪）
- 依据：`08-跨模块协作与端到端时序.md` 的"移动端接口契约"；`01` 的幂等键规范
- 独占文件：
  - 新增 `dev-docs/移动端接口契约.md`
- 做什么：
  1. 为七个扫码动作各写一节，每节固定包含：路径、HTTP 方法、入参字段表（名称、类型、必填、说明）、出参字段表、幂等键格式、错误码清单、扫码内容格式（扫的是什么码，怎么解析）。

     | 动作 | 对应领域动作 | 扫码内容 |
     | --- | --- | --- |
     | 收货 | `confirmArrival` | 到货单号 / 供应商送货单号 |
     | 上架 | `confirmInOrder` | 库位码 + 容器码 |
     | 拣选 | 出库分配与拣选确认 | 库位码 + 批次码 |
     | 领料确认 | `confirmMaterialReq` | 领料申请号 + 批次码 |
     | 开工 | `startOpTask` | 工序任务号 / 工单号 |
     | 报工 | `submitReport` | 工序任务号 |
     | 完工 | `finishOpTask` | 工序任务号 |

  2. 路径统一前缀 `/app-api/{模块}/{资源}/{动作}`，与后台 `/admin-api` 区分。
  3. 幂等键格式沿用 01 的四段规范，`sourceModule` 取 `APP`。
  4. 每个动作列出可能的业务失败原因与对应错误码（开工的五项门禁各自的错误码要列全），供移动端做友好提示。
  5. 附一节"未来实现说明"：说明 `controller/app` 包的建法、认证方式（复用 `app-api` 的鉴权）、与 `admin-api` 共用领域 Service 的原则。
- 不做什么：
  - **不写任何 app Controller 代码**
  - 不建 `controller/app` 包
  - 不改后端任何代码
- 验收：
  - 七个动作的契约完整（路径、入参、出参、幂等键、错误码五项齐备）
  - 幂等键格式与 01 一致
  - 错误码与实际代码里的错误码一一对应（在自查里贴出核对结果）
