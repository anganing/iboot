# 05 阶段 4 APS 进入执行闭环

- 版本：v1.0.0
- 目标：改一次工单交期，重排、发布、车间派工看到新计划，全链路无手工干预；缺料清单与齐套快照对得上。
- 依据：`dev-docs/业务流程/06-APS计划排程流程.md` 全文；`dev-docs/APS求解器开发规范.md`
- 任务数：4
- 前置：阶段 1 全部 31 个任务审查通过（本阶段可与阶段 2、3 并行）

## 阶段背景

APS 的场景、投影、求解、版本状态机、发布下达、缺料、负荷、任务锁定全链路已实现，测试 23 个类。剩下四件事：

1. 下达不推进 MES 工序任务状态，车间不知道计划已到
2. MES 执行闭环建成前投影里的工序进度全是初始值，重排会把在制工序当未开工
3. `aps_shortage` 与 `mes_kit_snapshot` 两套缺料数字并存，口径未对账
4. 部分代码风格违规

**不可协商的红线**（见 `APS求解器开发规范.md`）：Timefold 锁定 1.34.0；严禁出现 `moveThreadCount`、分区搜索、近邻选择、多阶段移动、约束剖析这些 Community 版会抛 `EnterpriseLicenseException` 的配置项；时间推导用声明式影子变量，不手写 `ListVariableListener`；约束名只在 `ApsConstraintNames` 里定义。

### T4-01 下达推进工序任务状态

- 依赖：T1-19（`OpTaskApiImpl` 已委托）
- 依据：`06-APS计划排程流程.md` 的"状态推进的缺口"；`04` 的"工序任务 9 态"
- 独占文件：
  - `iboot-module-mes/.../service/optask/OpTaskServiceImpl.java`（仅 `applySchedule` 方法）
  - `iboot-module-mes/src/test/java/.../service/optask/OpTaskServiceImplTest.java`（或新增测试类）
- 做什么：
  1. `applySchedule` 在更新 `res_id`、`planned_start_time`、`planned_end_time` 的同时，对当前状态为 `PENDING` 的任务把 `status` 推进到 `READY`（走 `MesOpTaskStateMachine`）。
  2. 已是 `READY` 的任务只更新计划时间与资源，状态不变。
  3. 已开工、已完工、已跳序、已取消的任务**继续跳过**（现有 `MesOpTaskStatusEnum.isNotStarted` 过滤保持不变）。
  4. 每条状态推进写一条 `mes_wip_txn`（`txn_type` 取 `START`，`from_status` 为 `PENDING`，`to_status` 为 `READY`，`biz_type` 标注排程下达，`biz_no` 取排程版本号），走 `MesWipTxnRecorder`，幂等键 `APS:{versionNo}:APPLY_SCHEDULE:{opTaskId}`。
     - `ApplyScheduleReqDTO` 需能带排程版本号：检查现有 DTO，若无则加 `versionNo` 字段（APS 侧 `ApsScheduleReleaseService.buildCommand` 同步传值）。
  5. 返回的生效条数口径不变（实际更新的任务数）。
  6. 测试：
     - `PENDING` 任务下达后变 `READY` 且有流水
     - `READY` 任务下达后状态不变，计划时间已更新
     - `RUNNING` 任务被跳过（计划时间未变）
     - 重复下达同一版本不产生第二条流水
- 不做什么：
  - 不改 `ApsScheduleReleaseService` 的过滤与事务逻辑（除传 `versionNo`）
  - 不改求解器任何代码
  - 不改版本状态机
- 验收：
  - 四个测试用例通过
  - `mvn -pl iboot-module-mes,iboot-module-aps -am test` 全绿

### T4-02 投影可信性验证与修正

- 依赖：T4-01，且阶段 1 的 T1-13 T1-14 已审查通过
- 依据：`06-APS计划排程流程.md` 的"投影可信性"
- 独占文件：
  - `iboot-module-aps/.../service/projection/source/MesOrderProjectionSource.java`（如需修正）
  - `iboot-module-aps/src/test/java/.../projection/` 下对应测试类
  - 新增 `dev-docs/开发任务安排/附-投影验证报告.md`
- 做什么：
  1. 造一份含在制工序的测试数据：一张工单 3 道工序，第 1 道 `DONE`（`completed_qty` 等于计划数），第 2 道 `RUNNING`（`completed_qty` 为计划数的一半，有 `actual_start_time`），第 3 道 `PENDING`。
  2. 跑投影刷新，dbx 查 `aps_projection_order`，逐字段核对：
     - 工序状态是否正确投过来
     - `completed_qty` 是否非 0
     - `actual_start_time` 是否投过来
     - 剩余量（计划数减已完成数）是否可推导
  3. 发现字段缺失或口径错误时修正 `MesOrderProjectionSource`。**只补投影字段，不改 MES 侧数据结构。**
  4. 跑一次求解，确认：
     - `RUNNING` 的工序被锁定（`lock_type` 为 `STARTED`）或至少不被排到过去的时间
     - `DONE` 的工序不参与排程
  5. 写 `附-投影验证报告.md`：记录测试数据、投影结果、发现的问题、修正内容、求解结论。
- 不做什么：
  - 不改求解器约束
  - 不改 MES 侧代码
  - 不改投影表结构（除必要补列，补列要在自查里说明理由）
- 验收：
  - 在制工序的 `completed_qty` 与 `actual_start_time` 进入投影（dbx 查询结果贴在自查里）
  - 已完成工序不被重排（求解结果为证）
  - 验证报告内容完整
  - `mvn -pl iboot-module-aps -am test` 全绿

### T4-03 缺料清单与齐套快照口径对账

- 依赖：T4-01，且阶段 1 的 T1-09 已审查通过
- 依据：`06-APS计划排程流程.md` 的"与齐套快照的对账"；`04` 的"三种发料方式的行为差异"
- 独占文件：
  - `iboot-module-aps/.../service/shortage/ApsShortageServiceImpl.java`（仅需求展开逻辑）
  - `iboot-module-aps/.../service/projection/kit/` 下相关类（如有）
  - 对应测试类
  - 新增 `dev-docs/开发任务安排/附-缺料对账报告.md`
- 做什么：
  1. 读 `MesKitRequirementExpander`（T1-09 建的）的需求展开逻辑，确认三点口径：
     - 损耗率公式：`父项数量 × 单位用量 ÷ (1 - 损耗率)`
     - `PHANTOM` 虚拟件不产生需求但向下展开子件
     - `BACKFLUSH` 倒冲件不计入
  2. 核对 `ApsShortageServiceImpl` 的需求展开是否用同一套口径。不一致则修正 APS 侧向 MES 侧对齐（MES 是齐套的权威口径，因为它直接服务开工门禁）。
  3. 造一份含三种 `issue_method` 的测试数据，同时跑齐套检查与缺料刷新，逐物料核对 `short_qty`。
  4. 允许的差异只有一类：时间差（投影刷新时刻与齐套检查时刻不同导致的可用量变化）。其余差异必须消除。
  5. 加一个对账测试：同一份数据下，两边同物料同工单的 `short_qty` 相等。
  6. 写 `附-缺料对账报告.md`：记录测试数据、两边数字、差异原因、修正内容。
- 不做什么：
  - 不改 MES 侧的齐套逻辑（APS 向 MES 对齐，不是反过来）
  - 不改求解器的 `MATERIAL_SHORTAGE` 约束
- 验收：
  - 对账测试通过
  - 对账报告内容完整

### T4-04 APS 代码风格整理

- 依赖：无
- 依据：《阿里巴巴 Java 开发手册》；`CLAUDE.md` 的编码风格约定
- 独占文件：
  - `iboot-module-aps/src/main/java/` 下存在风格违规的文件（先扫描定位，在自查里列出清单）
- 做什么：
  1. 扫描并修正四类违规：
     - **一行多方法**：`@Override public void a() { ... }` 挤在一行的，拆成正常缩进
     - **通配 import**：`import xxx.*;` 改为显式 import
     - **缺 `@Override`**：实现接口或覆写父类方法时补上
     - **字段挤行**：`@Resource private XxxService a; @Resource private YyyService b;` 拆成多行
  2. 扫描方式：`rg` 找 `import .*\.\*;`、找一行内出现两次 `public` 或 `private` 的行。
  3. **纯格式改动，不改任何逻辑**。改完 diff 里应当只有空白、换行、import 顺序的变化。
  4. 同时检查 MES 的 `api` 包下是否有同类问题（`OpTaskApiImpl` 有一行多方法的写法），一并整理。
- 不做什么：
  - **不改任何业务逻辑**
  - 不重命名、不抽方法、不调整类结构
  - 不动求解器的约束定义与权重
- 验收：
  - `rg "import .*\.\*;" iboot-module-aps/src/main/java` 无匹配
  - `mvn -pl iboot-module-aps -am test` 全绿（测试通过数与改动前一致）
  - 自查里列出改动文件清单与违规类型统计
