## 为什么单独列一个任务

前面每个任务书里已经写了各自的验证要求，但**逐任务验证过不等于整体可用**——单页能出数据，不代表工作台入口挂对了、菜单授权真的生效、双端都不翻车。本任务做整体验收，**不写新功能代码**。

### 4.5 【新增，2026-09-17】必须实调接口验证，不能只核对配置值

**背景（已发生的事故）**：M5 把 5 条移动端菜单的 `status` 改成 `1`，以为是"启用"，实际芋道的 `CommonStatusEnum` 是 **`0=ENABLE` / `1=DISABLE`**——结果**全部禁用**，超管登录后 `mobile-menu/my` 返回空数组，工作台一片空白。

M5 用 dbx 静态核对了配置值、主线程也复核了一遍，**双方都确认"数据是对的"，但没人真实调一次接口**。配置值正确 ≠ 行为正确。事故最终由老大于页面手动发现。

**M6 必须做到**：

1. **菜单接口实调**（不能只看数据库）
   ```powershell
   $body = '{"username":"admin","password":"admin123"}'
   $login = Invoke-RestMethod -Uri 'http://127.0.0.1:48080/admin-api/system/auth/login' -Method POST -ContentType 'application/json' -Body $body -TimeoutSec 10
   $h = @{ Authorization = "Bearer $($login.data.accessToken)" }
   $menu = Invoke-RestMethod -Uri 'http://127.0.0.1:48080/admin-api/system/mobile-menu/my' -Headers $h -TimeoutSec 10
   $menu.data.menus.Count
   ```
   **期望**：超管返回 **3 个分组**（消息通知 / MES 作业 / WMS 作业），共 **4 个入口**（消息中心、我的任务、批次追溯、库存查询）。
   （注：Git Bash 里的 `curl` 连不上该后端，**必须用 PowerShell 的 `Invoke-RestMethod`**。）

2. **凡是涉及 `status` / 布尔型 / 状态过滤的改动，一律实调接口确认返回，不接受"数据库值看着对"作为验收依据。**

3. **反向验证**：若某页期望有数据却为空，先怀疑状态字段的语义是否理解反了，去读对应的枚举定义（如 `CommonStatusEnum`），**不要凭直觉判断 0/1 的含义**。

4. **交叉验证手法**（推荐）：拿已知正确的同类数据做对照——例如判断 `system_menu` 的 `status` 语义时，看 PC 端 1044 条在用的菜单是什么值，一目了然。

### 5. 数据正确性抽查（用 dbx）

- **报工幂等**：连点两次后，`mes_prod_report` 只多一条；`mes_op_task.completed_qty` 只增一次
- **状态显示**：所有列表的状态列都是中文，全仓 grep 确认没有裸枚举值输出到界面
  ```bash
  grep -rn "RUNNING\|QUALIFIED\|PENDING" src/pages/ | grep -v "dict\|//\|type\|===" 
  ```
  （命中不等于有问题，逐条判断是否是把原始值直接渲染到界面）
- **时间格式**：确认显示为可读时间，不是裸时间戳数字
- **【重点】派工状态与工序状态不能串**：`src/pages/mes/task/index.vue` 的派工状态必须用 `dispatchTaskStatusLabel()`（待接单/已接单/作业中/已完成），**不能用 `opTaskStatusLabel()`**（那会显示成待排产/待开工）。这两套字典值域重叠但语义不同，串了不报错、只是显示错的中文。核实方式：确认列表里派工状态的文案是「待接单」而不是「待排产」。
